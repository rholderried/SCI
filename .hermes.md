# SCI — Project Context for Hermes

SCI (Serial Communication Interface) is a request-response, mostly-ASCII wire
protocol between a host ("Master") and an embedded device ("Slave"). This repo
holds the C implementation (both sides) and a Python host-side driver/tooling
layer. It's a solo-maintained embedded project, currently mid-refactor
(unifying previously separate Master/Slave codebases) and being documented.

Read this file before doing non-trivial work here. If you touch directory
structure, build/test commands, or resolve one of the "known issues" below,
update this file in the same commit/session — it's the only project context
file in this repo, read by Hermes and (if ever used here) other coding agents.

## Protocol shape (for orientation only — README.md is the spec)

Master/slave, request-response, framed with STX/ETX. Each device exposes a
"var struct": an array of `tsSCIVAR` descriptors (pointer, var-type, datatype,
optional callback), addressed by array index. Message types: GetVar (`?`),
SetVar (`!`), Command/RFC (`:`), Upstream (`>`), Downstream (`<`). Responses
carry ACK / DAT / UPS / NAK / ERR. Diagrams: `doc/layers.png`,
`doc/latex_img/*`.

## Directory map

- `C/Common/` — shared code used by both sides: `Buffer`, `Helpers`,
  `SCIDatalink` (link layer), and common headers. `SCICommon.h` defines the
  protocol version (currently 0.6.0), message-identifier chars, and the
  master/slave error enums.
- `C/Master/` — host-side stack: `SCIMaster`, `SCIMasterDataframe`,
  `SCIMasterTransfer`.
- `C/Slave/` — device-side stack: `SCISlave`, `SCISlaveDataframe`,
  `SCISlaveTransfer`, `VarAccess`, `CommandStucture.h`.
- `C/Test/` — unit tests on the Unity framework. `UnitTests.c` exercises
  `SCISlaveInit`/master+slave round trips against `TestCallbacks.c/h` and
  `VariablesAndCommands.c`. `C/Test/Unity` is a **git submodule**
  (`.gitmodules` → `ThrowTheSwitch/Unity`) and is NOT checked out by default.
- `C/config/SCIconfig.h` — build-time configuration (buffer sizes etc.).
- `Python/SCI.py` — host driver built on `pyserial`. Mirrors the C protocol:
  `CommandID`, `Datatype`, `Response`, `Command`, `Variable` classes; opens a
  real serial port (e.g. `SCI('COM3', 128, baud=2000000)`).
- `Python/Datalogger.py` — reads onboard datalogger channels via `SCI`;
  configured through a user-supplied `DataloggerCfg.py` (template at
  `Python/config/DataloggerCfg_Template.py`).
- `Python/HeaterController.py` — higher-level controller. **Imports
  `SerialProtocol`, which does not exist anywhere in this tree.** It predates
  the `SCI.py` rewrite (`Datalogger.py`/`SCI.py` use `Datatype`/`Variable`,
  this file uses an older `varType`/`Parameter` shape). Treat as broken/stale
  until someone ports it — don't assume it runs.
- `Python/Tests/testSCI.py`, `testDatalogger.py` — **not automated tests**,
  despite the name/location: they're manual smoke-test scripts that open a
  real serial port (`COM3`, `COM27`) against physical hardware, and
  `testDatalogger.py` also needs `matplotlib`. Don't run them expecting a
  pass/fail result without hardware attached; don't treat CI-style failure
  here as a code regression signal.
- `doc/` — protocol documentation: `layers.svg/png` (architecture diagram)
  and LaTeX-generated figures under `latex_img/` (message table, transmission
  ID, acknowledge types) referenced from `README.md`.

## Build / test

- **C unit tests (Windows/MinGW, per `.vscode/tasks.json` "Unit Test Build"
  task):**
  ```
  git submodule update --init          # first time only — pulls in Unity
  C:\MinGW64\bin\gcc.exe -g C\*.c C\Test\*.c -o C\Test\UnitTest.exe -I C -I C\Test
  ```
  Note the task's actual glob is `${workspaceFolder}\*.c` +
  `${workspaceFolder}\Test\*.c` with `${workspaceFolder}` = `C/` — i.e. it
  expects to be invoked with `C/` as the VS Code workspace root, not the repo
  root. Adjust paths if compiling manually from repo root. Output binary:
  `C/Test/UnitTest.exe` (a checked-in `C/Test/UnitTest` binary already exists
  from a prior build).
- **Python:** no formal test runner/config found (no `pytest.ini`,
  `setup.py`, or `requirements.txt` in the repo). `Python/Tests/*.py` are
  manual hardware scripts, not `pytest` suites — see note above.

## Branches

- `master` is the only branch, locally and on `origin`. Old pre-restructure
  feature branches (`feat/command_acknowledgement`, `feat/hex_format_transmission`)
  were deleted (both local and upstream) as no longer meaningful after the
  repo restructure.

## Workflow rules

- Never commit code changes directly on `master`. Create a new branch per
  change/feature (e.g. `feat/...`, `fix/...`) and work there; `master` stays
  the clean integration branch.
- Don't jump straight into editing code on request. The user plans changes
  explicitly before implementation — default to discussion/analysis and wait
  for the user to move into planning/execution mode before writing or
  changing files.

## Conventions

- Doxygen-style `/**...*/` file headers with a `<b> History </b>` changelog
  block at the top of each C file — follow this pattern in new/edited files.
- The var-struct design intentionally reinterprets values via `union` for
  cross-datatype access — this is undefined behaviour per strict ANSI C, but
  is a deliberate, tested tradeoff (see README "General" section). Don't
  "fix" this without discussing it — it's a known, accepted design choice.
- Dynamic memory allocation is used; the README flags this as a known
  MISRA-C compliance concern for constrained targets. Keep that in mind if
  targeting a MISRA-C environment.

## Hermes-specific notes

- This repo mixes two stacks (`C/` and `Python/`) with different toolchains
  that rarely touch the same files. When delegating with `delegate_task`,
  split C and Python work into separate subagents rather than one mixed
  task.
- Always check `git status` / `git branch` at the start of a session rather
  than assuming `master` is checked out or clean.
