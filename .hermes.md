# SCI — Project Context for Hermes

SCI (Serial Communication Interface) is a request-response, mostly-ASCII wire
protocol between a host ("Master") and an embedded device ("Slave"). This repo
holds the C implementation (both sides) only. It's a solo-maintained embedded
project, currently mid-refactor (unifying previously separate Master/Slave
codebases) and being documented.

The Python host-side driver/tooling layer that used to live in this repo
(`Python/`) has been moved out to its own repository and is no longer part of
this tree. This repo is now C-only, and the former `C/` wrapper directory has
been flattened away — `Common/`, `Master/`, `Slave/`, `Test/`, `config/`, and
`CMakeLists.txt` now live directly at the repo root.

Read this file before doing non-trivial work here. If you touch directory
structure, build/test commands, or resolve one of the "known issues" below,
update this file in the same commit/session — it's the only project context
file in this repo, read by Hermes and (if ever used here) other coding agents.

## Protocol shape (for orientation only — README.md is the spec)

Master/slave, request-response, framed with STX/ETX. Each device exposes a
"var struct": an array of `tsSCIVAR` descriptors (pointer, var-type, datatype,
optional callback), addressed by array index. Message types: GetVar (`?`),
SetVar (`!`), Command/RFC (`:`), Upstream (`>`), Downstream (`<`). Responses
carry ACK / DAT / UPS / NAK / ERR. Diagrams: `doc/layers.png`,
`doc/latex_img/*`.

## Directory map

- `Common/` — shared code used by both sides: `Buffer`, `Helpers`,
  `SCIDatalink` (link layer), and common headers. `SCICommon.h` defines the
  protocol version (currently 0.6.0), message-identifier chars, and the
  master/slave error enums.
- `Master/` — host-side stack: `SCIMaster`, `SCIMasterDataframe`,
  `SCIMasterTransfer`.
- `Slave/` — device-side stack: `SCISlave`, `SCISlaveDataframe`,
  `SCISlaveTransfer`, `VarAccess`, `CommandStucture.h`.
- `Test/` — unit tests on GoogleTest, built via CMake. `Test/gtest/`
  holds:
  - `SlaveTests.cpp` / `SlaveErrorTests.cpp` — Slave-only raw-byte tests
    (drive `SCISlaveReceiveData`/`SCISlaveStatemachine` directly, no
    Master). `SlaveErrorTests.cpp` covers error paths the Master's public
    API can't construct on purpose (bare Upstream request without a prior
    Command, unrecognized request identifier).
  - `RoundTripFixture.h` — shared scaffolding for every round-trip test
    file: a base `RoundTripTest` fixture (Slave init only) and
    `PumpUntilIdle()`, which pumps `SCIMasterSM()`/`SCISlaveStatemachine()`
    in lockstep until the Master returns to `ePROTOCOL_IDLE`. Each round-trip
    test file derives its own fixture from `RoundTripTest`, calls
    `RoundTripTest::SetUp()` first, then installs its own
    `tsSCI_MASTER_CALLBACKS` via `SCIMasterInit()`.
  - `RoundTripTests.cpp`, `RoundTripSetVarTests.cpp`,
    `RoundTripCommandTests.cpp`, `RoundTripErrorTests.cpp`,
    `RoundTripSequenceTests.cpp` — Master+Slave round-trip tests (both
    statemachines pumped in one process) covering GetVar, SetVar (incl.
    EEPROM-backed vars and the action-procedure callback), Command (all
    three response shapes: plain success, inline data, upstream — incl.
    multi-packet chunked upstream), invalid-number error paths, and
    back-to-back transaction sequencing. `RoundTripSequenceTests.cpp` also
    has a `SlaveTransferProcessRequestTest` suite that drives
    `SCISlaveTransferProcessRequest()` directly (Slave-only, no Master) to
    cover the "new command/upstream number vs. continuing transfer"
    branches that a Master-driven flow can't reach.
  - `MasterTestCallbacks.c` — the Master-side blocking TX callback shared
    by all round-trip tests.

  `TestCallbacks.c` and `VariablesAndCommands.c` provide the shared Slave
  fixture data/callbacks reused by all tests (`varStruct` has 7 entries:
  5 RAM vars, 1 EEPROM-backed var, 1 RAM var with an action-procedure
  callback; `cmdStruct` has 5 entries covering upstream/data/plain-success/
  large-upstream/argument-passing command shapes).
  `TestCallbacks.c`/`.h` also expose `g_forceEEPROMWriteFailure`, a test-only
  switch to force `SlaveWriteEEROM` to fail (exercises the SetVar
  EEPROM-write rollback path). `Test/config/SCIconfig.h` is the test
  suite's own SCI configuration, wired in automatically by
  `CMakeLists.txt` when `BUILD_TESTS=ON` (the default).

  **Fixed 2026-09-11** (was previously a known bug pinned by a test):
  `SCISlaveTransfer.c`'s `bNewCmd`/Upstream-number checks used to compare
  against `sResponseControl.sRsp.i16Num`, which
  `SCISlaveTransferInitiateResponse()` always stamps from the *current*
  request immediately before that comparison runs — making the
  number-mismatch half of both checks dead code (a new Command/Upstream
  number arriving mid-transfer was silently merged into the old transfer's
  state). Fixed by adding `tsRESPONSECONTROL.i16TransferCmdNum`
  (`SCISlaveTransfer.h`), set only when a request is recognized as
  genuinely new, and comparing against that instead. See
  `SCISlaveTransfer.c`/`.h`'s History blocks and
  `RoundTripSequenceTests.cpp`'s `SlaveTransferProcessRequestTest` cases
  (`NewCommandNumberIsRecognizedAsFreshMidTransfer`,
  `SameCommandNumberContinuesOngoingTransfer`,
  `UpstreamRequestWithMismatchedNumberIsRejected`) for the fix and its
  regression coverage.
- `config/SCIconfig_Template.h` — documented **template** for the
  build-time SCI configuration (buffer sizes, var/command struct sizes,
  EEPROM layout, etc.). Not compiled by this repo's build; copy it into your
  own project and adapt. Every SCI source file does `#include "SCIconfig.h"`
  unqualified and expects the integrating project/build to supply that
  header via its own include path — see `CMakeLists.txt`'s
  `SCI_CONFIG_DIR` cache variable.
- `doc/` — protocol documentation: `layers.svg/png` (architecture diagram)
  and LaTeX-generated figures under `latex_img/` (message table, transmission
  ID, acknowledge types) referenced from `README.md`.

## Build / test

- **C unit tests (CMake + GoogleTest, Windows/MinGW; tested with
  `cmake` 3.23, MinGW-W64 gcc/g++ 7.3.0):**
  ```
  cmake -S . -B build -G "MinGW Makefiles"
  cmake --build build
  cd build && ctest --output-on-failure
  ```
  The `sci` library requires an application-supplied `SCIconfig.h` via the
  `SCI_CONFIG_DIR` CMake cache variable (see `CMakeLists.txt`). It
  defaults to `Test/config` when `BUILD_TESTS=ON` (the default), so the
  commands above work with no extra flags. For a library-only build, pass
  `-DBUILD_TESTS=OFF -DSCI_CONFIG_DIR=<dir containing your SCIconfig.h>` —
  see `config/SCIconfig_Template.h` for a documented starting point.

  GoogleTest is pulled automatically by CMake `FetchContent` (pinned to
  `v1.15.2`) — no git submodule, but the first configure needs internet
  access. Test sources live in `Test/gtest/`; `Test/TestCallbacks.c`
  and `Test/VariablesAndCommands.c` provide the shared Slave fixture
  data and callbacks reused by all tests. `Test/gtest/RoundTripTests.cpp`
  is the only test that exercises the Master and Slave together in one
  process — everything else only covers the Slave in isolation.

## Branches

- `master` is the only branch, locally and on `origin`. Old pre-restructure
  feature branches (`feat/command_acknowledgement`, `feat/hex_format_transmission`)
  were deleted (both local and upstream) as no longer meaningful after the
  repo restructure.

## Workflow rules

- Never commit code changes directly on `master`. Create a new branch per
  change/feature (e.g. `feat/...`, `fix/...`) and work there; `master` stays
  the clean integration branch.
- Don't jump straight into editing code on request. The user plans changes
  explicitly before implementation — default to discussion/analysis and wait
  for the user to move into planning/execution mode before writing or
  changing files.

## Conventions

- Doxygen-style `/**...*/` file headers with a `<b> History </b>` changelog
  block at the top of each C file — follow this pattern in new/edited files.
- The var-struct design intentionally reinterprets values via `union` for
  cross-datatype access — this is undefined behaviour per strict ANSI C, but
  is a deliberate, tested tradeoff (see README "General" section). Don't
  "fix" this without discussing it — it's a known, accepted design choice.
- Dynamic memory allocation is used; the README flags this as a known
  MISRA-C compliance concern for constrained targets. Keep that in mind if
  targeting a MISRA-C environment.
